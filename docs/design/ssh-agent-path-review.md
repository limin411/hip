# SSH 智能体接入：路径评审与修订建议

> 状态：**评审材料 · 建议稿 v0.1** · 2026-08-02  
> 目的：对照分析 `terminal-agent-panel-spec.md`（v1.3，主路径）与 `remote-project-workspace-spec.md`（v0.1，搁置）后，给出评审结论与修订建议。  
> 说明：本文是评审存档；评审结论已并入 `terminal-agent-panel-spec-v2.md`（v2.5）。旧稿（v1.3 / workspace 搁置稿）已清理，备份于 `.temp/design-archive-2026-08-02/`。

## 0. 结论摘要

1. 两份方案不是并列的两个选择，而是同一问题（SSH 连上后 AI 以什么形态介入）的**两层答案**：终端方案回答「在终端旁配一个运维副驾」，工作区方案回答「把远程目录变成一等 Code 项目」。
2. **P0 走终端右栏智能体（terminal copilot）成立**：范围可控、与 hip 三进程架构（UI 握 PTY、sidecar 握 agent loop）天然契合、复用面大。
3. 但「远程当 Code 项目代价过大」应理解为**分阶段而非永久否决**；远程工作区是长期演进方向，今天的基础设施大部分可复用。
4. 真正被低估的风险不是代码工作量，而是**共享 PTY 的执行闭环**（完成检测、不确定性 UX、多会话上下文串扰），应作为 P0 关键路径优先设计。
5. 建议的增量修订：SFTP 只读提前到 P0、会话模型预留 `hostId`、把「命令可能仍在运行」设计为一等状态、补齐文档引用与决策记录。

## 1. 两份方案的本质差异

| 维度 | 终端右栏智能体（主路径） | 远程项目工作区（搁置） |
|------|--------------------------|------------------------|
| 用户故事 | 「对着这台机器问，帮我敲命令」 | 「打开一个项目，本地/远程只是根在哪」 |
| 会话心智 | 会话挂在 SSH 进程 `tm_*` 下，1:N | 会话 = Code 会话，绑定 `host + remotePath` |
| 能力边界 | 读终端上下文、经批准写共享 PTY；无可靠文件编辑 | 文件树 / 读写 / git / exec，完整 Code 面 |
| 主要成本 | 双轨焦点 + UI 侧工具桥 + surface 全链路 | WorkspaceBackend 抽象 + SFTP + 远程 git + 缓存 |
| 主要风险 | 共享 PTY 完成检测脆弱、会话生命周期短 | 工作量显著更大、延迟体验、安全面扩大 |

结论：两者**共用 90% 基础设施**（Host 库、SFTP、exec、ring、HITL、权限模型），真正分歧在「会话的父实体」——进程实例 vs 主机/项目。这个分歧决定了它们是阶段关系，不是替代关系。

## 2. 决策复盘

### 2.1 发生了什么

2026-08-02 当天：先选工作区方案（v0.1）→ 同日因实现面过大搁置 → 恢复终端方案（v1.3）。

### 2.2 评审意见

- 成本评估基本成立：工作区 P0 至少包含 WorkspaceBackend、SFTP 读写、路径 jail、远程 exec、git、缓存，是数周级工程；终端方案 P0 更接近一周级。
- 但注意：两个方案**都需要新能力**。工作区需要的是广度（多个子系统），终端需要的是深度（一个脆弱的执行闭环）。深度风险更隐蔽，不能因为「代码量少」就认为风险低。
- 建议把这次翻转的理由（成本/范围/时间评估）写进两份文档的修订记录，避免三个月后重新辩论。
- 表述上应明确：终端方案是**阶段一**，不是「远程 Code 项目的替代答案」。

## 4. 风险与修订建议

### R1 共享 PTY 完成检测（最高风险）

**现状**：完成启发式 = 空闲静默 + prompt 匹配 + 硬超时；超时不自动 Ctrl-C，返回部分输出。

**问题**：启发式会经常误判——`tail -f`、慢命令、交互式进程、用户同时输入都会触发假完成或假超时。P0 成功标准没有覆盖这些场景。

**修订建议**：

1. 把「命令可能仍在运行」设计为**一等状态**：工具结果默认带不确定性（`timed_out`、`partial`、`user_interleaved`），agent 不得虚构完成。
2. `terminal_read` 支持 turn 内轮询，允许 agent「先等一段再看」，而不是一次性 `wait_ms` 后定生死。
3. 允许 agent 在结果不确定时直接问用户「命令是否已完成」——比复杂启发式便宜且可靠。
4. 不自动 Ctrl-C 保持；危险命令黑名单按原计划 P1。
5. P1 再做 opt-in `__HIP_EC` 包装，但注明对别名 / 交互式命令的局限。

### R2 文件能力缺口

**现状**：P0 无 SFTP 写、无编辑器自动操作；SFTP 只读列为 Phase 2。

**问题**：运维任务最后一步通常是「改配置文件再重启」；P0 的 agent 只能诊断和建议，不能收尾。产品承诺（运维副驾）与能力（只能看）有落差。

**修订建议**：

- **SFTP 只读提前到 P0**（`sftp read` 复用 Files tab 同源通道，成本低）。
- **P1 增加「提议修改」闭环**：agent 提出 diff → 用户确认 → UI 写入或提示用户执行。
- 若产品坚持 P0 仅诊断，文档必须写明 persona（「诊断助手，不治疗」），避免用户预期错位。

### R3 会话生命周期与持久化

**现状**：`tm_*` 进程内 ephemeral；现网 close 直接从侧栏删除记录；原草案策略 A 关终端软删子会话；不做每 Host 跨 `tm_*` 记忆。

**问题**：P0 合理，但运维副驾一周后失忆会成为主要抱怨点；`tm_*` 作归属键也让未来重绑定困难。

**修订建议**：

1. `SessionConfig` 在 `managedTerminalId` 之外**同时记录 `hostId`**（冗余字段，成本约等于零），为 host 级记忆和未来 workspace 绑定留路。
2. **关闭 ≠ 删除**：P0 即改为「状态标识 + 记录保留」（spec v2.1 D12 修订），关闭后记录标记 `disconnected`、子会话保留只读；删除记录时确认后**级联软删其下对话（进回收站，可恢复）**；删除 Host 配置 = **级联清理记录与对话（进回收站，可恢复）**，无保留选项（spec v2.4 D14 / Q8）。
3. P1 候选：host 级「最近对话」查询入口（不改变绑定模型，仅按 hostId 过滤）。

### R4 多会话共享 ring 的上下文污染

**现状**：同一 `tm_*` 允许多会话，但 PTY 与 ring 是共享的；会话 A 发起的命令输出会进入会话 B 的上下文。

**问题**：模型容易把其他会话的操作当成自己的操作结果，导致错误推理。

**修订建议**：

- 切换子会话时注入系统注记：「终端状态自你上次对话后可能已变化，最近输出可能属于其他对话」。
- 保持 per-`tm_*` 单 flight 锁；`terminal_read` 返回带上限和截断标记。
- P2 可给 `ssh_write` 加 `source: 'user' | 'agent'`，仅用于遥测与调试。

### R5 exec 通道矛盾

**现状**：工作区方案 P0 推荐独立 exec channel；终端方案 D4 是共享 PTY。两份文档直接矛盾。

**评审**：这不是实现细节，而是产品取舍——可见性（共享 PTY，但竞态与完成检测脆弱）vs 可靠性（独立 channel，exit code 干净，但不可见、环境不一致）。

**修订建议**：

- P0 采用共享 PTY（可见性就是产品卖点），维持 D4。
- `ssh_write` 预留 `source` 字段，避免将来加独立 channel 时两套机制打架。
- 独立 channel 作为 Phase 2 进阶选项，与共享 PTY 按 surface / 工具区分，不混用。

### R6 surface 全链路（沿用 terminal spec §9.3 / §18）

- `surface:'terminal'` 的协议、过滤、profile 必须全链路落地，未知值禁止回落 code。
- 保持原实现切片：Slice 0（协议 + surfaceOf + 过滤 + profile）→ 2（UI tool 桥）未完成前不做对外演示。

## 5. 修订后的分期

### P0 — 终端智能体闭环（在原 spec §12 基础上增量）

1. 协议 `surface:'terminal'` + `managedTerminalId` + `hostId`；surfaceOf 全量过滤；profile 禁 `run_script`（沿用原切片 0）
2. 双轨焦点 + session 作用域 UI / HITL
3. UI tool 桥：批准 → `sshWrite` → `readSince` → 结果回传；**完成检测不确定性为一等状态**
4. **SFTP 只读（提前）**
5. 右栏 `files | agent` tabs + 侧栏 SSH 会话树 + 状态标识；`close(tm)` → **保留记录（`disconnected`）+ 会话只读**；重连复用同 `tm_*`
6. per-tm 单 flight；断线禁 exec；多会话切换注记；删除记录确认对话框（级联软删进回收站）；Host 删除关联（级联清理进回收站，无保留选项）

### P1 — 体验与闭环

- 完成检测增强：turn 内轮询、opt-in `__HIP_EC` 包装、超时后「问用户」路径
- 危险命令二次确认、TUI 黑名单
- **「提议修改」文件闭环（diff → 确认 → 写入）**
- hostId 级最近会话入口
- Context Slot / PanelTabBar / 右键重命名 / i18n 全量

### P2 — 增强

- `tm_*` 持久化与会话重绑；孤儿会话历史浏览
- SFTP 读写工具、选区解释、ACP 桥
- 删除记录时「连同删除对话」选项（默认保留）；write source 遥测

### P3 — 方向保留（非承诺）

- 远程工作区（WorkspaceBackend）作为独立演进路径，**P2 结束时复盘**再决定：
  - 数据：SSH 用户请求分布、终端使用时长、文件编辑/代码任务占比
  - 若远程代码任务占比高，优先做「最小 SshBackend：SFTP 树 + 读写 + ssh_exec」挂在 Code surface 上，而非完整工作区抽象
  - 届时复用：Host 库、SFTP 通道、HITL、ring、`hostId` 绑定

## 6. 成功标准（在 terminal spec §14 基础上补充）

1. 超时/长命令返回部分输出，agent 不虚构完成、不自动 Ctrl-C。
2. 用户中途输入不造成状态错乱，结果标记 `user_interleaved`。
3. 同 `tm_*` 多会话切换后上下文不串台（注记生效）。
4. 断线 / 关闭终端后无写入；**侧边栏记录与会话保留（状态标识），重连可继续**。
5. SFTP 只读可用：agent 能读远程文件并引用内容。
6. 本地 managed terminal 行为与现网一致（回归项保持）。
